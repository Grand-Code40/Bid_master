# Отправка и Inbox: проект изменений производной v23

Дата: 2026-11-03. Статус: предложение для согласования владельцем.
Основа: очищенная производная v23 из переданного архива, SHA256
`9b75020dcd52705ef3738fab0966aee5c37f394dde32875cfe1574751c5460c5`.
Это не побайтовая копия production. Исторический Python main сохраняется отдельно;
новый код находится в `panel/`. Публикация и production-миграции в задачу не входят.

## Проверенные ограничения и выбор

Worker/D1 уже обслуживает приватную панель, owner-only API и MCP. Sender отключён.
Очередь, подтверждение условий и журнал наблюдений есть; браузерного исполнителя нет.
Inbox хранит наблюдённые агентом email-уведомления, а не читает почтовый ящик.
Базовые синтетические тесты архива: 206/206, Node 24.17.0, сеть отключена.

Рассмотрены три пути:

1. Сохранить Worker/D1, добавить протокол отдельного доверенного исполнителя
   FL.ru/Freelance.ru, не объявляя его подключённым до реального preflight/readback;
   добавить настоящий клиент Gmail API для ограниченного чтения и отдельный приём
   наблюдённых сообщений площадок. Это предлагаемый путь: он сохраняет работающий
   стек и позволяет dot подключить сессии без публикации сессий или их переноса в Worker.
2. Вернуть исторический Python main и браузерный профиль Windows. Не подходит:
   другая схема и приложение, неизвестная совместимость с текущими данными.
3. Использовать Freelancer.com API как замену активным площадкам. API чтения и
   ставок существует, но источник в v23 архивирован. Его возобновление не входит
   в эту задачу и не решает доставку на FL.ru/Freelance.ru.

У активных площадок подтверждённого интегрированного API отправки нет. Worker
не может управлять браузером. Поэтому подключаемый транспорт — явная внешняя
зависимость; выдумывать селекторы, доступ к аккаунтам или работающий executor нельзя.

## Отправка

- Только owner + same-origin POST может начать отправку. Writer/MCP не получают
  право одобрять или отправлять. Weblancer блокируется независимо от каталога.
- Владелец проверяет точные source/order URL, revision, текст, аккаунт отправителя,
  аккаунт получателя, цену/валюту/срок и допустимый расход отклика. Обычное одобрение
  черновика/очередь не превращаются в разрешение отправки.
- Новый preflight вызывается сервером через фиксированный доверенный service binding
  `SENDER_SERVICE`; произвольный URL/токен/сессия из браузерного JSON не принимается.
  Исполнитель доказывает текущую сессию и состояние формы/заказа, а также отсутствие
  предыдущего отклика; доказательство имеет короткий срок и привязано к снимку.
- После owner-клика CAS атомарно фиксирует неизменяемый claim и случайный токен.
  Затем выполняется ровно один вызов внешней отправки с постоянным operation ID.
  Повтор запроса возвращает состояние первого claim, а не вызывает отправку снова.
- Sender service обязан иметь устойчивую идемпотентность по claim/operation ID и
  выполнить не более одного действия на площадке. Без этого сервис непригоден.
- Результат клика/HTTP 200 не означает sent. Отдельный readback должен вернуть
  совпадающие source/order, sender, recipient и точный текст с идентификатором
  публикации и временем наблюдения. Это проверка доверенного исполнителя,
  а не независимое доказательство прочтения клиентом.
- Таймаут, невалидный ответ, несоответствие текста или сбой после вызова транспорта
  дают uncertain; незавершённый sending после падения также блокирует повтор.
  Восстановление только чтением/readback, без повторного send. Недоказанное
  отсутствие отклика не считается not_sent. Ошибки preflight не начинают отправку.
- История и существующий guard manual delivery сохраняются. Изменение текста,
  отмена или установленная недоставка требуют нового одобрения.
- Кнопка показывает реальные статусы: не подключён, доступна проверка, отправка
  начата, опубликовано по readback, результат неизвестен. Пока service binding
  отсутствует, реальная отправка недоступна; очередь не маскирует этот факт.

## Inbox

- Сохранить mail_notifications и прежние MCP/API без переписывания старых строк.
  Новая аддитивная таблица хранит сообщения площадок; единый API объединяет их с
  уведомлениями, сохраняя разные kinds и происхождение.
- Наблюдения агента помечаются caller_observed, а не provider_verified.
  Письмо остаётся email_notification; оно не превращается в полную переписку.
  Сопоставление с заказом только по точному проверенному URL/идентификатору.
- Gmail-клиент использует только официальный HTTPS API с runtime OAuth secrets.
  Требуются явно настроенный mailbox и ограниченный notification query; по умолчанию
  чужая/вся почта не импортируется. getProfile проверяет аккаунт. Только GET к Gmail;
  никаких send/modify/mark-read, HTML, вложений и импортов кодов авторизации.
- Синхронизация ограничена по объёму. Курсор хранится приватно на сервере; успешная
  страница продвигает его после сохранения данных. Ошибка сохраняет прежние записи,
  сброс невалидного курсора виден как resync_required, неполная выборка явно помечена.
- В панели отдельная кнопка получения из подключённого канала. Обновление D1 каждые
  15 секунд не называется мониторингом Gmail. Автоматическое расписание не создаётся.
- Статус канала содержит last_attempt/last_success, режим ручной проверки, охват,
  причины пропуска/ошибки и задержку сохранения события в панель. Время email
  internalDate -> recorded_at не выдаётся за задержку ответа на площадке; у старых
  и наблюдённых данных неизвестное значение остаётся неизвестным.
- Ошибка/401/429/запрет/неподключённый канал различаются. Данные и сырые ошибки
  провайдера не попадают в публичные отчёты. Weblancer показывает paused и не опрашивается.

## Схема, миграции и интеграция

Только новые таблицы/индексы для provider sync status/cursors и сообщений площадок;
без удаления, пересоздания, переименования или массового backfill старых таблиц.
Проверить обе схемы (schema.sql и последовательность Drizzle migrations) и миграцию
заполненной синтетической v23: строки listings/reviews/mail/history остаются неизменными.
Не добавлять production project ID, OAuth значения, сессии, базы и персональные данные.
Каталожные фикстуры архива не являются реальными наблюдениями и не импортируются.

## Проверки и критерий результата

- Точный снимок и одобрение, чужой origin/identity/writer, Weblancer/неподдерживаемый
  источник, два одновременных send, повтор HTTP после потерянного ответа.
- Отмена до claim запрещает send; отмена после commit claim не притворяется отзывом
  внешнего действия. Воспроизводимые interleavings вместо нестабильного требования
  ровно одного fulfilled у допустимых последовательных confirm -> cancel.
- Таймаут после send, плохой/чужой receipt, падение до записи результата, read-only
  восстановление, сохранённые manual guards и старые operation hashes.
- Gmail пагинация/дубли/смена аккаунта/401/403/429/unsafe auth mail/неполная страница;
  unified keyset cursor, отдельные notification/message kinds и owner isolation.
- Owner UI: конкретный текст/адресат до клика, честный unavailable/uncertain,
  безопасное отображение текста и независимые ошибки источников.
- Все тесты синтетические с блокировкой сети. Live доставка и реальная почтовая
  авторизация остаются непроверенными до предоставления нужных подключений и
  отдельного одобрения владельцем конкретного внешнего действия.
