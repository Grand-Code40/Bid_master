# Подключение к производной v23

Код этой ветки — `panel/`, очищенная производная v23, а не точная production-копия.
Исторический Python-проект в корне не заменяет облачную панель. Production Site ID,
owner identity, D1 binding, writer secrets, база и сессии в эту ветку не входят.
Рабочую панель эта задача не развёртывает и её настройки не меняет.

## Отправщик

См. [контракт](SENDER_SERVICE.md). Нужен отдельный действительно работающий
исполнитель с приватным endpoint/журналом и проверенной сессией. `SENDER_ENABLED`
по умолчанию отсутствует/false. Конфигурация без успешного preflight показывает
configured_unverified. Пользователь подтверждает условия, проверяет свежий снимок,
затем нажимает «Отправить один раз». Очередь по-прежнему не означает отправку.

## Gmail

Конфигурировать только приватные runtime secrets/settings существующего Site:

- `GMAIL_MAILBOX` — конкретный авторизованный почтовый ящик;
- `GMAIL_NOTIFICATION_QUERY` — явно ограниченный Gmail query;
- `GMAIL_ACCESS_TOKEN` либо все три `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`,
  `GMAIL_REFRESH_TOKEN` уже согласованного OAuth подключения.

Токены не вставлять в Issue, chat, браузерную форму или Git. Не создавать новый
OAuth grant автоматически. Чтение тела требует разрешённого read-only scope;
проверить реальный аккаунт и права отдельно. Пример `.env.example` содержит
только названия, не рабочие значения. Старые OWNER_USER_ID/WRITER_TOKEN не заменять.

Поддержан конъюнктивный query длиной до 500 символов: положительный
`newer_than:1d` .. `newer_than:90d` плюс хотя бы один `from:`, `subject:` или `label:`.
OR, скобки, фигурные скобки, кавычки, backslash, `|` и `&` отклоняются, чтобы нельзя
было вынести часть запроса за ограничение возраста. Пример синтаксиса, не рабочая
настройка: `newer_than:30d label:PlatformNotifications`. Метка должна реально
существовать и содержать только разрешённые владельцем уведомления.

Один owner-click читает максимум 10 ID и их MIME из фиксированного Gmail REST.
getProfile сверяет настоящий mailbox. Секреты не попадают в D1 или браузерный
ответ. OAuth refresh — только к Google token endpoint. Никаких Gmail send/modify,
отметок прочтения, HTML, вложений и кодов авторизации. Небезопасные/неподдержанные
письма пропускаются с обезличенным счётчиком; покрытие всегда частичное. Конфликт с ранее сохранённым отрывком также виден как пропуск; исходная запись и её provenance сохраняются, следующие письма обрабатываются.

Курсор pageToken и lease хранятся приватно на сервере. Неполная страница требует
следующего явного клика. Ошибка сохраняет старые сообщения; временный сбой не
продвигает курсор. Подтверждённый устаревший pageToken сбрасывает ограниченный обход,
а rate limit соблюдает Retry-After. Смена mailbox/query изолирует курсор.

Фоновое расписание и Pub/Sub watch не создаются. Обновление UI каждые 15 секунд
читает только D1 и статусы, а не Gmail. `last_success` — завершение выборки фильтра;
не гарантия доставки новых событий после этой даты. Измерение у новых писем —
получение в Gmail -> сохранение в панели; начальный backlog и старые события не
включаются. Задержка площадка -> уведомление и полнота чатов остаются неизвестными.

Официальные источники: [Gmail sync](https://developers.google.com/workspace/gmail/api/guides/sync),
[message get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get),
[profile](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/getProfile),
[push requirements](https://developers.google.com/workspace/gmail/api/guides/push).
Текущий клиент выполняет ограниченный list/get polling, не обещает history/push sync.
Native Sites connector eligibility в среде не предоставлена; доступ через личный
Gmail tool агента не считается подключением Gmail к Worker.

## Сообщения площадок

`bid_record_platform_message` принимает одно наблюдённое сообщение с точной связью
с уже сохранённым заказом. Это caller_observed, не provider_verified и не полная
история чата. `bid_read_inbox` и `/api/inbox/unified` читают оба вида записей вместе;
старые bid_read_mail и /api/inbox остаются совместимыми. Просмотр отмечается только
в панели. Weblancer не опрашивается и не принимает новые platform messages.
Прямые API чатов активных площадок не подключены. Профили и каталог источников — dot.

## Миграция и применение diff

1. Сверить реальную текущую production-версию/схему и изменения dot. Синтетические
   URL/наблюдения архива не переносить в production. Не копировать весь архив поверх Site.
2. Владелец готовит приватный backup и проверенный план восстановления вне GitHub;
   ни дамп, ни клиентские строки для проверки кода не нужны.
3. Для базовой v23 согласована только новая `0004_chubby_supreme_intelligence.sql`:
   пять новых таблиц/индексы; originals 0000..0003 не меняются и не выполняются снова.
   Проверить миграционный журнал. Не подключать пустую D1 вместо рабочей базы.
4. Перенести функциональный diff на фактические исходники, сохранив текущие
   Site identity, D1 binding, runtime secrets, owner-only access и сессии исполнителя.
   `.openai/hosting.json` здесь очищен (`project_id:null`) и не является production config.
5. Сначала проверить на отдельной синтетической схеме/развёртывании. Реальные
   подключения, hosted readback и конкретная отправка требуют самостоятельной
   проверки и отдельного одобрения владельца; этот PR их не выполняет.
